# Monday release evidence and cycle records

This contract is for implementation and review. It does not activate publishing or replace the existing manual release policy.

Use one scheduled Codex task for all seven weekly dispatches from the [Monday design](weekly-production-design.md). Claude uses one separate reviewer routine. The Tuesday watchdog runs in GitHub Actions.

## Reservations and cycle outcome

Derive the slot from the actual dispatch time with `weeklySlot`. Reserve `weeklyReservationKey(slot)` before any editorial write or image dispatch. The reservation must use a create-only Git ref under a dedicated reservation namespace. A pre-existing ref, a concurrent creation conflict or an uncertain response means stop before mutation. A list-then-comment sequence is not a lock. Never use an upsert, update or force operation for the reservation. Point each reservation at an immutable evidence commit unique to that dispatch, recording the provider and run ID. Two contenders must never reuse the same evidence commit. Re-read the resulting ref and record it in the cycle ledger. After an uncertain response, compare the ref with that dispatch's evidence commit for reconciliation only. A matching ref does not authorise replay of work whose completion is uncertain. A retry can reconcile existing work but cannot repeat an uncertain mutation. Prove this with competing writers before activation. Confirm rulesets allow reservation ref creation and that no workflow triggers on these refs.

The cycle ledger records the Tuesday cycle key, actual Zurich slot, task and provider IDs, reservation ref, selected candidate, PR, reviewed heads and review/image budgets. It links evidence rather than reproducing mutable scores. Record exactly one terminal outcome (Published, Deferred, Blocked) under the unique `<cycle>/outcome` key with the same create-only reservation discipline. A merge with unverified deployment is pending. Tuesday's watchdog checks the prior cycle outcome and pauses if it is absent.

## Evidence

Before review, commit a weekly intent keyed by Tuesday cycle and article ID, with the intended Monday date, paths and hashes. Do not add a published entry or a ready review to the candidate's manual JSON files. An intended publication date is not a publication claim. The record's article and both cover hashes are SHA-256 of the exact Git bytes. The weekly check reads those bytes directly from Git without running candidate scripts. Keep the existing published and manual records valid.

For the eligible review slot, the author and independent reviewer each return a separate exact-head receipt containing article ID and exact Git paths, cycle, head, review slot, role, provider, article and cover scores, hashes of all three assets, a readiness decision and findings. Their ledger entries link the evidence for sources and browser verification. Read the genuine provider review evidence through the authorised surfaces and verify its provenance before accepting a receipt. Provider strings inside candidate files or PR comments are not proof of identity. If provenance is unavailable, block. Compare budgets with the complete ledger rather than trusting candidate counters. A weekly candidate must record at least one and at most four successful image generations.

`assertWeeklyRelease` validates the date, hashes, ratings, findings and budget shape. It does not fetch Git data, authenticate receipts, lock a slot, check branch protection or merge. The trusted integration must do those things separately. The dedicated required check must fail closed on missing, stale or ambiguous evidence and must be proven in the ruleset before activation. `validateWeeklyRelease` binds the intent to the article ID and the article's parsed main and share image paths, then projects a publication and ready review from the verified receipts into memory and passes the combined records to the existing validator. The caller derives the article path and parses the article from those same hashed Git bytes. Existing manual JSON records are left intact. The production build must consume a trusted, durable projection tied to the verified merge tree, including previously released weekly articles on subsequent builds. The current Cloudflare Git build has no such input wired. Prove fail-closed build integration, persistence across subsequent deployments and manual-release compatibility before activation. Reconcile the public deployment before marking Published.

## Integration checks before activation

The reservation adapter calls GitHub's create-ref endpoint and reads the returned ref back before granting the slot. Its test races two attempts against a fake API. The next integration check must use the actual scheduled credential and namespace, with two concurrent requests and one successful owner. Require an active branch ruleset targeting the entire `refs/heads/weekly-reservations/**` namespace. Allow creation, restrict updates and deletions, block force pushes, and configure no bypass actors. The scheduled credential may share the Owner identity, so enforce immutability in the ruleset. With that credential, probe and record in the activation ledger the live two-request race, successful readback, and refusal of update, deletion and force push. A failure keeps activation off.

Cloudflare currently deploys a build from `main` and the release catalogue reads `editorial/publications.json`. The existing release gate also needs a ready review record. A candidate intent on `main` therefore remains invisible in production. Establish and independently review the trust path for the durable projection before modifying that catalogue. Use a separate protected branch, `refs/heads/weekly-release-ledger`, outside `main`. The Cloudflare build must explicitly fetch this ref using read-only repository access. Do not assume it is reachable from the checkout. Only a dedicated ledger GitHub App may update the ref. Keep its credential and the ledger signing key in a protected Actions environment restricted to `main`. Ordinary Actions tokens, candidate workflows and scheduled editorial credentials must have no bypass. The writer workflow runs trusted main code, verifies provenance and the exact reviewed head and merged tree, and permits only append-only fast-forward ledger updates. Verify the App cannot write to protected `main`. The proposed access and key setup require separate implementation and verification before activation.

Pin the ledger verification public key in trusted build configuration. Verify signatures over the ledger snapshot and each release's article identity, cycle, reviewed head, merge commit, date and asset hashes. Require the release's merge commit to be an ancestor of the actual Cloudflare checkout and verify the checked-out bytes again. Verify that the signed snapshot covers every weekly intent in that checkout before publishing, including previous releases. An unavailable fetch, missing or stale entry, invalid signature or ambiguous history fails the production build and leaves the last good deployment serving. Deployments with only manual release records continue using the existing path. Prove read-only fetch access, writer isolation, snapshot completeness and failure behaviour in the actual build environment before activation.

The activation test must show that a weekly intent alone stays out of production, a verified intent enters the release catalogue, a later build retains verified older releases, and missing or tampered evidence blocks the weekly release. Run this before enabling the single Codex task or Claude's recurring routine.
